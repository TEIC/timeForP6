What do we mean by P5’s Abstract Model?

A document is said to conform to the TEI Abstract Model if features for which an encoding is proposed by the TEI Guidelines are encoded within it using the markup and other syntactic properties defined by means of a valid TEI-conformant schema. Hence, even though the names of elements or attributes may vary, a TEI-conformant document must respect the TEI Semantic Model, and be valid with respect to a TEI-conformant Schema. Although it may be possible to transform a document which follows the TEI Abstract Model into a TEI-conformant document, such a document is not itself conformant.

As noted above, the notion of semantic conformance cannot be completely enforced in a formal way. The TEI conceptual model is expressed by means of formal specification in a customization file, by means of descriptive prose in the body of these Guidelines, and implicitly by examples of usage. Any inconsistency between, for example, the text of these Guidelines and a part of a specification should be considered an error and reported to the TEI Council for correction.

Classes and models are confusing

  • P5 class system introduces confusions over what belongs where, and why it belongs there.
  • We have 86 different attribute classes as of Guidelines release 4.12.0. (Think we have enough now?)
  • How did att.global.rendition get this way? Why do we need three attributes for describing rendering in the source text?

Over time, problems intensify

  • When P5 was launched, Council was established to maintain and update it.
  • Consistency in updates was difficult / impossible over time
  • It becomes difficult to figure out how to introduce requested features without tripping over problems with the conformance constraints.
  • Stylesheets and infrastructure to maintain P5 is complicated in a brittle way to try to introduce to new Council members.
  • We need a more robust system.

What we want for P6

  • We need context-dependent content models.
  • Constraints need to be meaningful, not applied to reconcile or compromise for validity.
  • We will still encode in XML, but TEI should also be readily expressible in other formats (e.g. graph models).
  • TEI concepts come first: express them as elements or attributes as needed.

How will P6 be different from P5?

  • Simplify: Reduce redundancies and points of confusion.
  • Make it easier to customize, with more expressive possibilities in modeling.
    • P6 Guidelines should centrally provide interactive support for customization processes.
    • P6 Blueprint modeling: Expresses customization decisions that may be shared and reviewed.
  • Prioritize scholarly decision-making process for determining how to mark up texts.

But P5 is not all bad! What aspects of P5 should continue in P6?

  • The TEI header!
    • Highly expressive modeling of document metadata for which TEI is widely known / heralded
    • Problematic: Extremely and perhaps unnecessarily prescriptive.
    • Nevertheless, an excellent place for standardizing data exchange.
  • Capacity to prepare many kinds of output data from the same "ground" source TEI document.
  • Encoding in XML and tree structure for ease of processing
    • e.g. standOff data structures together with trees for preparing editions and data
  • Multiple encoding methods => encoding methods can be chosen adequately to the methods in your project.
  • We identified this as a problem: P5 has too many ways of doing the same thing, but it is only not the thing that has to be done, but also the way it is done that needs to be appropriate.
    • e.g. nested/treelike approaches vs. standoff markup/pointer based vs. milestones.
  • Remember: the TEI vocabulary works like a lingua franca for digital scholarly editions (and other fields) and needs to be retained.
    • e.g. when we talk about <pb>, every other edition nerd understands we are talking about page-beginning.

Is this P6 worth the trouble? Isn’t P5 fine to continue?

  • Not worth building P6 if it continues to replicate the same kinds of problems
  • P5 can continue to develop (add new features) while P6 is being designed.
    • P5 : P6 :: Python 2 :: Python 3
  • P6 needs to be easier to maintain: Needs modifications to the infrastructure.
  • Changes the role of Council in splitting our work for a while.
  • If P6 is to develop: needs support for dedicated meetings, consultation with experts.
